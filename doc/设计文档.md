# 工程三维 GIS 引擎设计文档

> 基于 three-tile 架构思想的工程级三维 GIS 引擎
> 
> 设计哲学：osgEarth 架构思想 × Cesium Native Tile Engine 模式 × Three.js Renderer

---

## 一、设计目标

构建一个接口驱动、高度解耦、可扩展的工程级三维 GIS 引擎。

**核心原则：**
- 所有数据保持原始工程坐标，不进行投影转换
- 统一 Project CRS 空间（如 CGCS2000 GK114），所有图层对齐到同一坐标系
- GPU 精度通过 Local Origin + Floating Origin 双层解决
- 每层只依赖接口，不依赖实现 — 用户可替换任何一个环节

**支持：**
- CRS：CGCS2000 GK111/GK114、EPSG:3857、UTM、自定义 Project CRS
- 底图：XYZ/WMTS（通过 proj4 重投影到 Project CRS）
- 叠加层：GeoTIFF、DEM、GeoJSON、DXF、PointCloud、GPR

---

## 二、总体架构

```
                        Engine (顶层入口)
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        LayerManager    TileManager    CameraController
              │              │              │
         ILayer[]      TileScheduler   FloatingOrigin
              │              │
    ┌─────────┼─────────┐   TileCache
    │         │         │
  ITileScheme IDataSource ILayerRenderer
    │         │         │
  (如何分块)  (数据哪来)  (如何渲染)
```

**数据流向（单向）：**

```
IDataSource.load(tileKey)
       │                    ← 纯数据，不知道 Three.js 存在
       ▼
  raw data (Image / GeoJSON / ArrayBuffer / Float32Array)
       │
       ▼
ILayerRenderer.createContent(rawData)
       │                    ← 变成 Three.js 对象
       ▼
  TileContent (含 RenderObject[])
       │
       ▼
ILocalOrigin.worldToLocal(content.origin)
       │                    ← 减原点，保证 GPU 精度
       ▼
  scene.add(renderObjects)
```

## 三、CRS 坐标系架构

### 3.1 设计原

整个引擎只有一个 Project CRS。所有数据（XYZ 底图 + Project Tile 叠加层）都在这个统一平面坐标系中。

### 3.2 坐标链路

```
经纬度 (lon, lat)
    │
    ▼  IProjectCRS.project(lon, lat)
CRS 平面坐标 (x, y 米)        ← 百万级，CPU 计算
    │
    ▼  ILocalOrigin.worldToLocal()
Local 坐标 (小数值)            ← GPU 安全
    │
    ▼
Three.js Mesh.position + Geometry
```

### 3.3 基础类型与接口定义

```ts
/** CRS 空间中的点坐标 */
interface CrsCoord {
  x: number;  // 东向 (米)
  y: number;  // 北向 (米)
  z: number;  // 高程 (米)
}

/** CRS 空间中的包围盒 [xmin, ymin, xmax, ymax] */
type CrsBounds = [number, number, number, number];

/** 投影接口 */
interface IProjectCRS {
  readonly name: string;
  readonly units: "meter" | "degree";
  
  /** 经纬度 → CRS 平面坐标 */
  project(lon: number, lat: number): { x: number; y: number };
  /** CRS 平面坐标 → 经纬度 */
  unproject(x: number, y: number): { lon: number; lat: number };
}
```

### 3.4 实现类

| 实现 | 说明 | 依赖 |
|------|------|------|
| `Proj4CRS` | 支持任意 EPSG 代码 | proj4 (可选) |
| `CGCS2000GKCRS` | 内置高斯-克吕格公式 | 无 |
| `UTMCRS` | 内置 UTM 公式 | 无 |
| `CustomCRS` | 用户传入 project/unproject 函数 | 无 |

### 3.5 XYZ 底图的坐标转换

XYZ 底图（EPSG:3857）通过 proj4 重投影到 Project CRS。

**问题**：XYZ Tile 在 3857 下是正方形，但投影到 GK114（横轴墨卡托）后，四个角是非矩形的弯曲四边形。只用 4 个顶点 + 矩形 PlaneGeometry 会导致纹理扭曲和边界错位。

**方案：GPU 细分网格 + 自适应密度**

借鉴 OpenLayers 的逐像素重投影思想，但将计算从 CPU 移到 GPU：

```
XYZ Tile (3857)
    │
    ▼  proj4 算 N×N 个顶点的 CRS 坐标（不是只有 4 个角）
    │
    ▼  在 CRS 下生成细分网格（zoom 小 → 8×8=64顶点，zoom 大 → 2×2=4顶点）
    │
    ▼  GPU 在顶点间插值纹理坐标
    │
    ▼  Mesh → 场景
```

**核心原则**：用多一些顶点换精确性。64 个顶点的 proj4 计算是微秒级。GPU 负责纹理插值，天然处理弯曲。

与 OpenLayers 的对比：
| | OpenLayers | 本引擎 |
|---|---|---|
| 方法 | Canvas 2D 逐像素重投影 | GPU 细分几何体 + 顶点插值 |
| 开销 | 256×256 = 65536 次/CPU | 8×8 = 64 次/CPU |
| 适用 | 2D Canvas | 3D WebGL |

Proj4 重投影只在加载时发生一次。

## 四、TileScheme — 双方案、统一接口

### 4.1 接口定义

```ts
interface ITileScheme {
  readonly name: string;
  
  /** 给定视锥体和 CRS，返回可见的 TileKey 集合 */
  getTilesInView(frustum: Frustum, crs: IProjectCRS): TileKey[];
  
  /** 给定 TileKey，返回 CRS 空间包围盒 */
  getTileBounds(key: TileKey): CrsBounds;
  
  /** 父 / 子 Tile 关系 */
  getParentKey(key: TileKey): TileKey | null;
  getChildKeys(key: TileKey): TileKey[];
}
```

### 4.2 XYZTileScheme（底图）

- 传统 Web Mercator 四叉树 (`x, y, z`)
- 内部封装 3857 → CRS 的 proj4 重投影
- `getTilesInView()`: 相机视锥 → CRS 范围 → 反算 3857 经纬度 → 计算可见 z 层级和 x/y 范围

适用：XYZ/WMTS 在线瓦片服务（底图）

### 4.3 ProjectTileScheme（工程叠加层）

- 按米分块：`tileX = floor(worldX / tileSize)`
- 纯平面网格，不涉及投影转换
- `getTilesInView()`: 相机视锥 → CRS 范围 → `x / tileSize` 整除 → tile 行列范围

适用：GeoTIFF、DEM、DXF 等工程数据

### 4.4 TileKey 设计

```ts
type TileKey = {
  schemeId: string;        // 绑定到具体的 TileScheme
  id: string;              // scheme 内部的 key（如 "14-12345-6789" 或 "1024-7308"）
  level: number;
};
```

两个 Scheme 的 Key 结构不同，用 `schemeId` 区分。

## 五、Tile & TileManager & TileCache

### 5.1 Tile 数据结构

```ts
interface Tile {
  id: string;
  key: TileKey;
  bounds: CrsBounds;         // CRS 空间包围盒
  origin: CrsCoord;          // Local Origin 点
  state: TileState;          // unloaded → loading → loaded → visible
  contents: TileContent[];   // 同一 Tile 可同时有 raster + dem + vector
}
```

**与 three-tile Tile 的关键区别：**
- 不继承 `Object3D`（解耦数据层和渲染层）
- `origin` 内置，每个 Tile 自带 Local Origin
- `contents` 是数组而非单体

**Tile 共享机制**：同一个 `TileScheme` 下的多个 Layer 拍到同一个 `TileKey` 时，共享同一个 `Tile` 实例。各 Layer 各自创建 `TileContent`，追加到 `tile.contents[]`：

```ts
// Layer "正射影像" 和 Layer "DEM" 都在 ProjectTileScheme(500) 下
// 拍到同一个 TileKey → 共享 Tile
Tile {
  key: "1024-7308",
  contents: [
    RasterContent { layerId: "ortho", data: ImageBitmap, renderObjects: [...] },
    RasterContent { layerId: "dem",   data: Float32Array, renderObjects: [...] },
  ]
}
```

好处：Cache 命中率高、同一个 Tile 只需一份元数据。

**场景锚点**：每个 Tile 在场景中对应一个 `THREE.Group` 作为锚点。每帧渲染时统一计算：

```ts
// 每帧：
group.position.set(
  tile.origin.x - floatingOrigin.current.x,
  tile.origin.y - floatingOrigin.current.y,
  0
);
```

正在加载的 Tile 也是如此——加载完成后 `mesh` 加入 `group`（相对坐标 `0,0,0`），`group.position` 已被 Floating Origin 修正。不存在"加载完成时原点已变"的时序问题。

### 5.2 TileManager

```
每帧流程:
  1. Camera → 计算一次 Frustum（所有 Layer 共享）
  2. Camera Extent → CRS 空间范围
  3. getVisibleLayers() → 扁平列表
  4. for each visible Layer:
       - TileScheme.getTilesInView(frustum, crs)  // 传入共享 frustum
       - 检查 layer.dependsOn → 依赖的 tile 已加载？
  5. TileScheduler → 合并去重、优先级排序
  6. Load Queue → 按优先级消费（MAX_PER_FRAME = 2~4）
  7. for each tile:
       - 查 Cache → 命中则直接显示
       - 未命中 → 加载 → ILayerRenderer.createContent(data, tile)
         → 顶点减 tile.origin → RenderObject[] → 挂到 Tile Group
         → floatingOrigin.register(group)
```

**Layer 依赖处理**：当 Layer A `dependsOn` Layer B 时，TileManager 在调度 A 的 tile 前先确认 B 的同 key tile 已 loaded。如果 B 的 tile 还在 loading，A 的 tile 排队等待。

### 5.3 TileScheduler 调度优化

**优先级模型（四维加权）：**

```
priority = 
  w1 × screenArea(tile)        // 屏幕占比大 → 先加载
+ w2 × 1/distToCenter          // 距屏幕中心近 → 先加载  
+ w3 × isInFrustum(tile)       // 视锥内优先
+ w4 × parentLoadedFirst(tile) // 父 Tile 已加载 → 优先
```

**帧预算控制：**
- 每帧最多加载 `MAX_PER_FRAME` 个 tile（2~4），防止卡帧
- 超出的排到下一帧

**渐进式显示：**
- 视锥内 → 低分辨率先显示 → 高分辨率替换 → 永不留白
- 视锥外 → 低优先级加载，不阻塞视锥内的

**加载取消：**
- Tile 离开视野且正在加载 → `AbortController.abort()` → 释放槽位

**显示过渡：**
- Tile 加载完成 → mesh.opacity 0→1（0.3s fade-in），消除闪烁感

### 5.4 TileCache

```ts
interface ITileCache<T> {
  get(key: string): T | null;
  set(key: string, value: T): void;
  has(key: string): boolean;
  remove(key: string): void;
  trim(maxSize: number): void;      // maxSize = GPU 内存字节数
}
```

**缓存粒度**：缓存的是 `Tile` 元数据。`TileContent` 作为 Tile 的 contents[] 成员，独立管理生命周期。当 Cache 淘汰 Tile 时：
1. 遍历 `tile.contents[]`
2. 调用每个 Content 的 `dispose()`
3. 触发 `RenderObject.dispose()` → GPU 资源释放 + FloatingOrigin.unregister

这样即使一个 Layer 隐藏，其他 Layer 的 Content 不受影响。

- 默认实现：`LRUTileCache`（LRU + GPU 内存上限，单位：字节）
- 可替换为 IndexedDB 等持久化实现

### 6.1 Layer 接口

```ts
interface ILayer {
  id: string;
  name: string;
  type: "raster" | "vector" | "volume" | "pointcloud";
  visible: boolean;
  opacity: number;
  zIndex: number;
  
  tileScheme: ITileScheme;
  dataSource: IDataSource;
  renderer: ILayerRenderer;
  
  /** 本层依赖的其他 Layer — TileManager 保证依赖的 tile 先加载 */

```

**Layer 是胶水** — 组合三个独立组件：

| 组件 | 职责 | 谁提供 |
|------|------|--------|
| `ITileScheme` | 这层按什么分块 | 引擎内置 |
| `IDataSource` | 数据从哪来 | 每种数据格式实现 |
| `ILayerRenderer` | 怎么变成 Three.js Object | 每种渲染类型实现 |

### 6.2 LayerManager

组织多个图层，支持分组管理：

```ts
interface ILayerGroup {
  id: string;
  name: string;
  visible: boolean;         // 一键控制整组
  opacity: number;
  layers: ILayer[];
  
  addLayer(layer: ILayer): void;
  removeLayer(id: string): void;
}

interface ILayerManager {
  groups: ILayerGroup[];
  
  addGroup(group: ILayerGroup): void;
  removeGroup(id: string): void;
  addLayerToGroup(layer: ILayer, groupId: string): void;
  
  // 排序控制
  moveUp(layerId: string): void;
  moveDown(layerId: string): void;
  moveToGroup(layerId: string, groupId: string): void;
  
  // 给 Scheduler 用
  getVisibleLayers(): ILayer[];  // 扁平化、按 zIndex 排序
}
```

**设计要点：**
- Group 只做组织，不影响调度逻辑
- z-index = 数组顺序，越靠后越靠前渲染
- Group 的 visible/opacity 向下传播到子 Layer
- Scheduler 看到的是扁平列表

## 七、Local Origin & Floating Origin

### 7.1 问题

工程坐标是百万级大数（如 `512345.123`），直接给 GPU 的 float32 会损失精度。

### 7.2 双层解决

**Layer 1 — Local Origin（每个 Tile 独立）：**
- `tile.origin = { x: 512000, y: 3654000 }`（取整对齐）
- Geometry 顶点：`worldCoord - origin = localCoord`（小数值，GPU safe）
- TileContent 不存自己的 origin，使用 `tile.origin`
- Mesh 挂载在 Tile 的 Group 锚点下，Group.position = origin - floatOrigin

**Layer 2 — Floating Origin（全局，随相机移动）：**
- 相机离开当前原点超过阈值（如 500m）→ 触发平移
- 所有 Tile 的 Group.position 更新偏移量，相机归零
- 只改 position，不重建 geometry

### 7.3 接口

```ts
/** Local Origin 接口：世界坐标 → 局部坐标 */
interface ILocalOrigin {
  /** 取整对齐：将坐标取整到 tileSize 的整数倍 */
  snap(worldCoord: CrsCoord, tileSize: number): CrsCoord;
  /** 世界坐标 → 局部坐标 */
  worldToLocal(world: CrsCoord, origin: CrsCoord): CrsCoord;
  /** 局部坐标 → 世界坐标 */
  localToWorld(local: CrsCoord, origin: CrsCoord): CrsCoord;
}

interface IFloatingOrigin {
  readonly current: CrsCoord;     // 当前原点
  readonly threshold: number;     // 触发阈值（米）
  readonly dirty: boolean;        // 本帧是否发生了平移（优化用）

  update(cameraWorldPos: CrsCoord): boolean;  // 返回 true 表示发生了平移
  register(tileGroup: Object3D): void;
  unregister(tileGroup: Object3D): void;
}
```

**性能优化 — Dirty Flag**：只有在 `floatingOrigin.dirty === true` 的帧，才遍历所有 loaded Tile 更新 Group.position。绝大多数帧原点不变，跳过 O(n) 遍历。

```ts
// TileManager 每帧：
floatingOrigin.update(cameraWorldPos);
if (floatingOrigin.dirty) {
  for (const tile of loadedTiles) {
    tile.group.position.set(
      tile.origin.x - floatingOrigin.current.x,
      tile.origin.y - floatingOrigin.current.y,
      0
    );
  }
}
```

## 八、DataSource — 多数据格式

### 8.1 接口

```ts
interface IDataSource<T = unknown> {
  dataType: string;
  crs: IProjectCRS;       // 数据自身的 CRS（声明用途，引擎不自动转换）
  bounds: CrsBounds;      // 数据范围（必须在 Engine CRS 坐标系下）
  
  /** 返回的数据坐标必须是 Engine CRS 坐标 */
  fetch(key: TileKey, tileBounds: CrsBounds): Promise<T>;
  dispose(data: T): void;
}
```

**CRS 转换责任边界**：DataSource 的输出坐标必须是 Engine CRS 坐标。如果数据自身的 CRS 与 Engine CRS 不一致，转换是 DataSource 内部的事。引擎不处理、不检测、不自动转换。

```ts
// 示例：GeoTIFF 是 GK111，Engine 是 GK114
// DataSource 内部负责 GK111 → GK114 转换
class GeoTIFFSource implements IDataSource {
  async fetch(key: TileKey, tileBounds: CrsBounds): Promise<ImageData> {
    const raw = await readGeoTIFF(this.url, tileBounds);
    if (this.dataCRS.name !== this.engineCRS.name) {
      return reproject(raw, this.dataCRS, this.engineCRS);
    }
    return raw;
  }
}
```

### 8.2 各数据格式

| DataSource | 输入 | 输出 | 关键实现 |
|------------|------|------|----------|
| `XYZTileSource` | URL 模板 | `ImageBitmap` | URL 替换、createImageBitmap |
| `GeoTIFFSource` | .tif 文件 | `{ imageData, geotransform }` | geotiff.js 按范围读取 |
| `DEMSource` | .tif 文件 | `Float32Array` (高程) | geotiff.js 读高程波段 |
| `GeoJSONSource` | .geojson 文件 | `Feature[]` (按 tile 裁剪) | 全量加载 + 空间裁剪 |
| `DXFSource` | .dxf 文件 | `DXFEntity[]` (按 tile 裁剪) | 全量解析 + 空间裁剪 |
| `PointCloudSource` | .las/.laz/.ply | `{ positions, colors, intensities }` | 按 tile 流式读取 |
| `GPRSource` | 探地雷达数据 | `VoxelGrid` | 数据→体素网格插值 |

### 8.3 注册机制

```ts
DataSourceRegistry.register("geotiff", GeoTIFFSource);
DataSourceRegistry.register("dem", DEMSource);
DataSourceRegistry.register("geojson", GeoJSONSource);
DataSourceRegistry.register("dxf", DXFSource);
DataSourceRegistry.register("las", PointCloudSource);
DataSourceRegistry.register("gpr", GPRSource);
DataSourceRegistry.register("xyz", XYZTileSource);

// 用户自定义
DataSourceRegistry.register("my-format", MyCustomSource);
```

## 九、Web Worker 策略

### 9.1 原则

与渲染无关的重计算全部放到 Web Worker，保持主线程流畅。

### 9.2 入 Worker 的操作

| 操作 | 说明 | 
|------|------|
| GeoTIFF 解码 | geotiff.js 的 `readRasters()` |
| DEM 高程采样 | Float32Array 生成、Martini 网格简化 |
| proj4 重投影 | N×N 顶点坐标转换（§3.5） |
| GeoJSON/DXF 解析 + 空间裁剪 | 大文件解析 |
| 点云流式读取 + 滤波 | LAS/LAZ 解析 |

### 9.3 实现

```ts
// DataSource 内部可以选择是否用 Worker
class GeoTIFFSource implements IDataSource<ImageData> {
  async fetch(key: TileKey, tileBounds: CrsBounds): Promise<ImageData> {
    // 在 Worker 中解码 GeoTIFF
    const workerPool = getWorkerPool("geotiff-decoder");
    return workerPool.exec({
      url: this.url,
      bounds: tileBounds,
      targetCRS: this.engineCRS,
    });
  }
}
```

- 使用共享 Worker Pool，限制并发数（如 navigator.hardwareConcurrency - 1）
- Worker 内部不依赖 Three.js，只做纯数据计算
- 主线程收到结果后交给 `ILayerRenderer` 创建 Three.js 对象

**Phase 1 不强制**，但从接口设计上预留：`IDataSource.fetch()` 返回 `Promise<T>`，天然支持 Worker 异步模式。

## 十、Renderer — 数据 → Three.js 对象

### 10.0 ILayerRenderer 接口

```ts
interface ILayerRenderer<TData = unknown> {
  readonly name: string;
  
  /** 从原始数据创建 TileContent（含 RenderObject[]） */
  createContent(data: TData, tile: Tile): Promise<TileContent>;
  
  /** 更新已有 TileContent（用于数据刷新场景） */
  updateContent?(content: TileContent, data: TData, tile: Tile): Promise<void>;
  
  /** 释放 RenderObject 的 GPU 资源 */
  disposeContent(content: TileContent): void;
}
```

**DEM 归属**：DEM 作为独立的 `RasterLayer`（`type: "dem"`），不跟影像绑定。需要地形的影像 Layer 在 Renderer 配置中传入 DEM Layer 的引用（编译期检查）：

```ts
const demLayer = new RasterLayer({
  name: "高程", type: "dem",
  tileScheme: new ProjectTileScheme(500),
  dataSource: new DEMSource({ url: "./dem.tif" }),
});

const orthoLayer = new RasterLayer({
  name: "影像",
  tileScheme: new ProjectTileScheme(500),
  dataSource: new GeoTIFFSource({ url: "./ortho.tif" }),
  renderer: new RasterRenderer({ 
    qualityTier: new DemMesh({ demLayer }),  // 传引用，不是字符串
  }),
});
```

**Layer 数据依赖声明**：Layer 接口增加 `dependsOn`，告诉 TileManager 加载顺序：

```ts
interface ILayer {
  // ...
  /** 本层依赖的其他 Layer（这些 Layer 的 tile 必须先加载） */
  dependsOn: ILayer[];
}
```

TileManager 调度时，对于有 `dependsOn` 的 Layer，先确保依赖的 tile 加载完成，再加载自己的 tile。避免影像先渲染成平地再突然隆起的问题。

好处：DEM 可独立开关、独立更新、被多个影像层共享、不跟具体影像耦合。

| 质量等级 | 几何体 | 适用 |
|----------|--------|------|
| `SimplePlane` | 平面 PlaneGeometry | 无 DEM |
| `DemMesh` | 顶点 z = DEM 高度 | 有 DEM |
| `SkirtedMesh` | 带裙边防裂缝 | 有 DEM + LOD 变化 |

```
Image/ImageBitmap → Texture → MeshStandardMaterial / MeshBasicMaterial
DEM Float32Array → 修改顶点 z → BufferGeometry
```

### 10.2 VectorRenderer（GeoJSON + DXF）

**DXF 加载策略（Phase 3）**：Phase 3 采用全量解析 + 按 tile 空间裁剪。标注文件大小建议 <50MB。大型 DXF 的流式解析（DXF 是顺序章节格式，可分段读）放入后续 Phase 优化。

| Geometry 类型 | Three.js 输出 | 优化 |
|--------------|---------------|------|
| Point | `InstancedMesh` | 大量点共享材质 |
| LineString | `BufferGeometry` + `LineBasicMaterial` | RTC 减原点 |
| Polygon | `ShapeGeometry` + earcut 三角剖分 | 支持带洞 |
| ExtrudedPolygon | `ExtrudeGeometry` | 建筑/体块 |

DXF 实体映射：

| DXF Entity | Three.js |
|------------|----------|
| LINE / POLYLINE / LWPOLYLINE | `Line` (BufferGeometry) |
| ARC / CIRCLE | 离散采样 → `Line` |
| SPLINE | 等距采样 → `Line` |
| TEXT / MTEXT | `Sprite` (CanvasTexture) |
| 3DFACE | `Mesh` |
| INSERT (Block) | 递归展开 → `Group` |

**符号化策略：**

```ts
interface IMaterialFactory {
  createLineMaterial(feature: Feature): Material;
  createFillMaterial(feature: Feature): Material;
  createPointMaterial(feature: Feature): Material;
}
```

用户注入 `IMaterialFactory` 来控制样式（单色线、虚线、面填充、拉伸体）。

### 10.3 VolumeRenderer（GPR）

```
VoxelGrid → Data3DTexture → BoxGeometry + ShaderMaterial (Ray Marching)
```

体素数据加载为 3D Texture，通过 Fragment Shader 做光线步进，支持等值面与 alpha 合成。

### 10.4 PointCloudRenderer

```
positions[] → RTC 减原点 → THREE.Points(BufferGeometry, PointsMaterial)
```

大点云用**八叉树 LOD** — 远处稀疏采样，近处原始密度。

### 10.5 TileContent

```ts
interface TileContent {
  id: string;
  tileKey: TileKey;
  layerId: string;                   // 所属 Layer
  data: unknown;                     // 原始数据
  renderObjects: RenderObject[];     // Three.js 对象（顶点已是 tile.origin 的局部坐标）
  state: ContentState;
}

interface RenderObject extends Disposable {
  object: Object3D;
}
```

> **注意**：TileContent 不存自己的 `origin` 字段。所有的 origin 统一在 `Tile.origin` 上，避免冗余和不一致。Renderer 创建 RenderObject 时，直接用 `tile.origin` 做减法转换顶点坐标。

## 十五、GPU 内存管理与资源释放

### 15.1 问题

`LRUTileCache` 淘汰 Tile 时，`TileContent` 里的 Three.js Object（geometry、material、texture）必须显式调用 `.dispose()`。如果遗漏，GPU 内存泄漏。

### 15.2 方案：Disposable 基类 + Cache 强制释放

```ts
abstract class Disposable {
  private _disposed = false;
  
  abstract dispose(): void;
  
  protected assertNotDisposed() {
    if (this._disposed) throw new Error("Already disposed");
  }
}

class TileContent extends Disposable {
  dispose() {
    this.renderObjects.forEach(ro => ro.dispose());
    this.renderObjects = [];
    super._disposed = true;
  }
}

class RenderObject extends Disposable {
  constructor(
    public object: Object3D,
    private floatingOrigin: IFloatingOrigin
  ) { super(); }
  
  dispose() {
    this.floatingOrigin.unregister(this.object);  // ← 关键：解除 Floating Origin 引用
    this.object.traverse(child => {
      if (child instanceof Mesh) {
        child.geometry?.dispose();
        if (Array.isArray(child.material)) {
          child.material.forEach(m => m.dispose());
        } else {
          child.material?.dispose();
        }
      }
    });
    this.object.removeFromParent();
  }
}

// LRUTileCache 淘汰时强制释放：
class LRUTileCache<T extends Disposable> {
  trim(maxSize: number) {
    while (this.size > maxSize) {
      const evicted = this.evict();
      evicted.dispose();  // 强制释放 GPU 资源
    }
  }
}
```

`Tile`、`TileContent`、`RenderObject` 都继承 `Disposable`。Cache 淘汰时沿引用链一路 `dispose()`。

## 十六、设计决策与边界澄清

以下是在设计评审中识别并已解决的全部问题：

| # | 问题 | 决策 | 位置 |
|---|------|------|------|
| 1 | XYZ 底图投影后不是矩形，纹理扭曲 | GPU 细分几何体（N×N 顶点）+ 自适应密度，zoom 小→8×8，zoom 大→2×2 | §3.5 |
| 2 | 两个 TileScheme 边界不对齐 | XYZ 底图本身已在 Engine CRS 下（通过 proj4），ProjectTile 也在同一 CRS 下。不存在两个不同 CRS 混合 | §4 |
| 3 | GeoTIFF 自身 CRS ≠ Engine CRS | DataSource 输出必须是 Engine CRS 坐标，转换是 DataSource 内部的事。引擎不管 | §8.1 |
| 4 | Floating Origin 切换时，加载中的 Tile | Tile 通过 `THREE.Group` 锚点挂载，每帧重算 `group.position`，不受加载时序影响 | §5.1 |
| 5 | 多个 Layer 共享 Tile 还是各自独立 | 共享 Tile 实例。不同 Layer 拍同一 TileKey 得同一 Tile，各自追加 contents[] | §5.1 |
| 6 | DEM 数据归属 | DEM 是独立 RasterLayer，影像 Layer 在 Renderer 配置中引用 DEM Layer ID | §9.1 |
| 7 | 大型 DXF 加载策略 | Phase 3 全量加载 + 建议 <50MB。流式解析后续 Phase 做 | §9.2 |
| 8 | GPU 内存释放 | `Disposable` 基类，Cache 淘汰时强制 `dispose()`，沿引用链释放 GPU 资源 | §15 |
