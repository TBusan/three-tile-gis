# 代码审查 + 低帧率性能/架构优化

## Context

用户请求："回头看看现在修改的代码有啥bug，然后已经存在的bug有什么可以优化性能、以及架构的地方。现在的帧率不高。"

上一轮完成了 OSM 换底图、ImageBitmap 预翻转（flipY）修复、相机方位角修正。本轮对全部热路径（demo 渲染循环、TileManager、TileScheduler、PerspectiveMapController、RasterRenderer、XYZTileSource、GeoTIFFSource、各 quality 网格、两个 tile scheme、cache）做完整审查。

**审查结论摘要**：
- **最近修改的 flipY / 方位角代码正确**（测试覆盖，无 bug）。
- 找到 **4 个真实 bug**（1 个导致倾斜视角顶部灰带 + 近侧调度浪费；1 个选项失效；1 个内存无界增长；1 个共享瓦片潜伏 bug）+ 1 处死代码。
- **低帧率根因**：6km 默认视角下瓦片数仅 ~50-100（`_pickZoom` 分辨率选级自动平衡），稳态 draw call 不是瓶颈。真正的每帧 CPU 成本在 demo `syncScene()` 每帧全量遍历 + `isTileHidden()` 祖先链字符串分配、`updateHUD()` 每帧 5 次 DOM 写（布局抖动），以及导航期调度排序 + 瓦片加载/纹理上传 churn。
- **架构观察**：场景结构性同步应事件/节流驱动而非每帧；恒等/无重投影瓦片的几何可共享。

## 一、审查结论（含文件:行号）

### A. 最近修改代码 — 正确，无 bug
- `XYZTileSource.createImageBitmap(blob, { imageOrientation: "flipY" })` + `RasterRenderer texture.flipY = false`：位图第 0 行 = 南端，上传原样，网格 v=0 = 南端。一致。
- `GeoTIFFSource._rastersToBitmap` 同样预翻转；`_computeWindow` row 0 = 北端，与 flipY 后第 0 行 = 南端正确衔接。
- `initialAzimuth = -π/2`（相机正南俯瞰，屏幕上方 = 北）：7 个测试覆盖。

### B. 正确性 bug

1. **`PerspectiveMapController.extent` 倾斜补偿错误**（`camera/PerspectiveMapController.ts:145-177`）
   - 现实现用 `halfH·tan(vFov/2)·dist·min(1/cos(θ), 4)` 对称扩展，近/远不分。
   - 45°/6km 时：相机可见地面实际跨度 **y ∈ [target−3.1km, target+11.6km]**，但 extent 只覆盖 **y ∈ [target±4.9km]** → **屏幕顶部出现灰带（未调度的远端地面）**，近侧又过度覆盖（-4.9km vs 实际 -3.1km）。
   - 宽度同样失真：远端可见半宽 ~16.7km vs 当前 14.5km，近端 ~4.5km vs 14.5km（浪费）。
   - 倾斜角越大灰带越宽；同时近侧多调度无用的瓦片，占用 `MAX_TILES_PER_VIEW` 预算。
   - **修复**：改为计算屏幕四角视线与地面 z=0 的交点取 AABB（标准 footprint 算法，见 Phase 1）。

2. **`minPolarAngle` 选项从未生效**（`camera/PerspectiveMapController.ts:102`）
   - 接口文档：默认 0.15（约 8.6°）"防止高海拔时完全锁死旋转"。但 L102 硬编码 `this.controls.minPolarAngle = 0`，`options.minPolarAngle` 存入 `this._minPolarAngle` 后只在 update() 动态 maxPolarAngle 钳位用。
   - 完全正俯视时 OrbitControls 的 `makeSafe()` 会让方位角退化 → 视图抖动风险。
   - **修复**：`this.controls.minPolarAngle = this._minPolarAngle`。

3. **`TileManager._nullLayers` 无界增长（内存泄漏）**（`manager/TileManager.ts:72, 866-871`）
   - 空瓦片（矢量层无要素区域返回 null）记录 `_nullLayers.set(memKey, Set<layerId>)`，只在同瓦片同层后续成功产出内容时 `delete`（L859）。
   - 空瓦片永不产出内容 → 条目永久残留。长时间平移浏览可积累数万条目（每条目一个 Set），Map 查找也在 `_addKeyRequest` 每次调度时累计变慢。
   - **修复**：加容量上限 `NULL_LAYERS_MAX = 8192`，超限清空重建（同 `TileScheduler._loadedParents` 模式，仅影响"空瓦片跳过"精度，无正确性影响）。

4. **共享瓦片迟到 content 回插已 dispose 瓦片（潜伏 bug）**（`manager/TileManager.ts:881-892`）
   - 场景：同 key 多层共享瓦片。A 层 content 已加载入 cache，加载期间 `evict()`/`cache.trim()` 因内存预算把该瓦片淘汰并 **dispose**；随后 B 层 content 迟到完成，L891-892 把含已 dispose renderObject 的 tile 重新 `set` 回 `_loadedTiles` + cache → demo `syncScene` 把已释放 GPU 资源的 mesh 挂回场景 → 渲染已 dispose 资源。
   - 当前 demos 各层 scheme 不同、key 不共享，不触发；但引擎 API 允许共享瓦片，是潜伏 bug。
   - **修复**：加载完成处过滤 `tile.contents` 中已 dispose 的 content（`content.disposed === true`）；过滤后为空则走失败/取消分支。

5. **`TileScheduler.hasPending()` 死代码**（`manager/TileScheduler.ts:171-176`）
   - O(n) 线性扫描，从未被调用（grep 无调用点）。删除。

### C. 低帧率性能分析

- **稳态瓦片数低**（`XYZTileScheme._pickZoom` 按分辨率选级，瓦片数随缩放自平衡）：6km 默认 → z14 ≈ 48 底图瓦片 + ~75 矢量瓦片 ≈ 100 draw call，不是瓶颈。
- **每帧热点（demo 层）**：
  1. `syncScene()` 每帧调用（4 个 demo 的 render() 内，如 `webmercator.ts:599`）：遍历全部 `loadedTiles`，对每个 tile 调 `isTileHidden()` → 祖先链每层 `tileKeyToString(parent)` **分配字符串** + 2 次 Map 查找。z16 时 ~450 tile × 16 层 ≈ 7200 次字符串分配/帧，且 100ms 节流的引擎调度期间结果不变。
  2. `updateHUD()` 每帧 5 次 DOM `textContent` 写（`webmercator.ts:682-690`）→ 每帧强制 style/layout 重算。
- **导航期热点（引擎层）**：
  3. `TileScheduler.schedule()` L129：优先级在 sort 比较器内重复计算，O(n log n)×2 次 `_computePriority`（含 Map 查找）。
  4. `_evictStaleZoomTilesContinuous`（L671）：每 100ms 对每个非当前 zoom 瓦片 `getChildKeys()` 分配 4 个 TileKey。（低优先）
  5. 瓦片加载 churn：4-8 瓦片/帧 → 纹理上传 + mipmap 生成 + 网格创建 + GC（导航期固有，受上面各项放大）。

### D. 架构观察
1. **场景结构性同步应事件/节流驱动而非每帧**：tile 加载/淘汰都发生在 100ms 节流内，`syncScene` 的结构性遍历可以对齐到 100ms；每帧只需保留淡入/淡出动画。
2. **恒等/无重投影瓦片的几何可共享**：ProjectTileScheme 瓦片（`reprojector` 为 null）同 (quality, level, bleedUV) 几何全同；XYZ 在 targetCrs 即为 3857 时同样全同。可缓存共享 BufferGeometry，省每瓦片创建 + GPU 上传 + computeVertexNormals。
3. **extent 应基于真实可视地面 footprint AABB**（见 B1）。

## 二、实施计划

### Phase 1 — 正确性修复（引擎 + 测试）

**1.1 `extent` footprint AABB**（`PerspectiveMapController.ts:145-177`）
- 用相机矩阵计算屏幕四角视线与地面(z=0)的交点：
  - `fwd = normalize(target - camPos)`；`right = normalize(cross(fwd, (0,0,1)))`；`up2 = cross(right, fwd)`。
  - 四角方向 `d = normalize(fwd ± right·tan(hFov/2) ± up2·tan(vFov/2))`。
  - `d.z < 0` 时：`t = -camPos.z / d.z`，地面点 `= camPos + t·d`，取 4 点 x/y 的 min/max。
  - `d.z >= 0`（视线越过地平线）→ 该方向用 `MAX_EXTENT_HALF` 钳位（沿用现有常量）。
- 保留 `MAX_EXTENT_HALF` 硬钳位；`resolution` getter 不动。
- 预期效果：45°/6km 下 extent 北界从 +4.9km → ~+11.6km（灰带消失），南界收窄（近侧浪费减少）。瓦片数增加约 1.7×（默认 ~48→~84），仍远低于 `MAX_TILES_PER_VIEW=512`。
- **测试**（`camera/__tests__/PerspectiveMapController.test.ts`）：新增 45°/6000 下 `extent[3] > target.y + 10000`；纯俯视（`initialPolarAngle≈0.01`）时 extent 接近无倾斜矩形；现有 finite/单调断言保持通过。

**1.2 `minPolarAngle` 生效**（`PerspectiveMapController.ts:102`）
- `this.controls.minPolarAngle = this._minPolarAngle`（替换硬编码 0）。
- **测试**：构造默认后断言 `ctrl.controls.minPolarAngle === 0.15`。

**1.3 `_nullLayers` 容量上限**（`TileManager.ts`）
- 加 `private static readonly NULL_LAYERS_MAX = 8192`；在 L866-871 记录新条目处检查，超限 `this._nullLayers.clear()`。
- **测试**（`manager/__tests__/TileManager.test.ts`）：灌入 9000 个不同 memKey 后断言 Map.size ≤ 8192。

**1.4 共享瓦片 disposed-content 守卫**（`TileManager.ts:881`）
- `tile.contents = tile.contents.filter((c) => !c.disposed)`，然后按现有逻辑走 `length > 0` / `hadFailure` 分支。
- **测试**：构造"加载期间被 cache.trim 淘汰"场景（mock LRU trim），断言迟到 content 不重新挂回。

**1.5 删 `hasPending`**（`TileScheduler.ts:171-176`）
- 删除方法与其注释。grep 确认无调用后删。

### Phase 2 — 性能优化（4 个 demo + 引擎）

**2.1 demo `syncScene` 100ms 节流**（4 个 demo 的 render()）
- 在 render() 顶部：`const now = performance.now(); if (now - lastSyncTs > 100) { syncScene(); lastSyncTs = now; }`（`lastSyncTs` 初值 0）。
- `syncScene()` 内部的淡入起点设置只在节流执行时发生；淡入/淡出动画在 render() 中每帧独立推进，不受影响。
- 新瓦片出现 ≤100ms 延迟（与引擎 `UPDATE_INTERVAL_MS` 天然对齐）；floating origin 移动、共享 content 补挂同样延迟 ≤100ms，可接受。
- 改动文件：`webmercator.ts:599`、`main.ts:712`、`epsg4326.ts:573`、`cgcs2000.ts:563`（各自 render() 内）。

**2.2 demo `updateHUD` 合并进 500ms FPS 统计块**（4 个 demo 的 render()）
- 把 `updateHUD(...)` 调用从每帧移到 `fpsElapsed >= 500` 的块内（与 fps 刷新同频，HUD 每秒刷新 2 次）。
- 消除每帧 5 次 DOM 写。改动文件同上。

**2.3 `TileScheduler.schedule()` 排序预计算优先级**（`TileScheduler.ts:129`）
- `unique.map(r => ({ r, p: this._computePriority(r) }))` → 按 p 降序 sort → map 回 `LoadRequest[]`。
- 语义不变，测试现有排序断言应保持通过。

### Phase 3 — 架构优化

**3.1 恒等/无重投影瓦片几何共享**
- `RasterRenderer` 加 `private _geomCache = new Map<string, BufferGeometry>()`；key = `${this.quality.constructor.name}|${level}|${bleedUV}`；**仅当 `tile.reprojector` 为 null/undefined 时**查缓存/复用，否则照旧新建。
- 共享几何的 RenderObject disposeFn 不再 dispose 共享几何（新增"是否共享"标记或由 RasterRenderer 在 dispose 时统一释放缓存）；`disposeContent` 仍只释放纹理。
- 同时 `XYZTileScheme.getReprojector`（`XYZTileScheme.ts:257-278`）加 identity 短路：`if (this.targetCrs.name === this._wm.name) return null`（需确认 `WebMercatorCRS.name === "EPSG:3857"`）。这样 webmercator 底图也走非重投影路径 → 共享几何 + 省逐顶点投影。
- 收益：矢量/DEM/GeoTIFF 层（Project 瓦片）+ 3857 底图每瓦片省一次 BufferGeometry 创建/上传/computeVertexNormals。
- **测试**（`RasterRenderer.test.ts`）：同 (level, bleedUV, 无 reprojector) 两次 createContent 复用同一 geometry 实例；有 reprojector 时不共享；dispose 不重复释放共享几何。

### 不做 / 低优先级
- `_evictStaleZoomTilesContinuous` 的 `getChildKeys` 分配（每 100ms、量小）。
- 单 zoom 原子 LOD 与"远/近分辨率分级"（架构性大改，破坏原子 LOD 设计）。
- 矢量 `_clip` 真多边形裁剪（跨瓦片要素 overdraw 仅在矢量层可见时，当前数据量小）。
